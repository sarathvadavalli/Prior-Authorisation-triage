# Golden acceptance coverage

The source requirements are `SPEC.md` and `rules.md`, including the user's final workflow clarification: missing required inputs return `pending_info` with no outcome; supplied evidence that fails a condition returns `pending_info` with outcome `Needs info`, displayed as Needs more info. Approve and Clinician review have `completed` status. Red flags always take precedence.

Only golden tests are used. Expected values are authored independently of the implementation; exact explanations, rule IDs, evidence gaps, statuses, and outcomes are compared. Existing cases are deliberately revised when an approved requirement changes, never automatically regenerated from engine output.

## Run

```powershell
python -m pytest tests/test_golden.py tests/test_app_golden.py -q
```

The suite contains 134 named cases: 22 contracts, 20 referrals, 66 procedure decisions, and 26 UI scenarios. Each engine decision case is executed twice against its fixed expectation. UI scenarios may contain several independently checked checkpoints.

Pending explanation format is checked in every pending engine/UI golden expectation: a short summary names the procedure and rule context, while only evidence gaps contain actionable details. `procedures.json`: `mri-40-days-keeps-details-only-in-evidence-gaps` records the requested 40-day MRI example. Unknown red-flag responses reference R2 in the explanation without assigning rule IDs or an outcome.

## Scope of the evidence

The suite tests function results and Streamlit-rendered elements with AppTest; it does not launch a browser, compare screenshots, or verify responsive layout or visual accessibility. The synthetic input surface is captured by visible-widget expectations. No identifiers or records are used in the fixtures. Source review complements these golden checks for the absence of patient-data storage, clinical-service calls, report interpretation, and an LLM; golden results alone do not prove those architectural properties.
